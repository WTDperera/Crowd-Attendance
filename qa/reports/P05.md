New sessions use `round_schema: 2`, immutable UID→registration roster data and `roster/{uid}` proofs, `rounds_started`, `scans_performed` and `active_round_id`. Observation identity is the document path `active_sessions/{sessionId}/rounds/{roundId}/observations/{studentUid}`. Root summaries use the generated Firestore session ID followed by a dot and base64url UID; nested summaries use UID. The raw session namespace supports an authorized missing-document transaction read. New generated session IDs contain no dot; this scheme is not a migration of legacy IDs.

Session creation checks the module enrollment count and every captured profile inside the write transaction; inconsistent counts/changing profiles reject creation. Each immutable proof is also authorized against the student's enrollment at atomic session creation. Later unenrollment does not rewrite the captured roster. Ambiguous/missing registration labels and deleting profiles fail closed. Registration changes during an active class fail closed; no unresolved registration format/case/byte-budget policy was invented.

Marks atomically create the observation and update root/nested summaries. Only the first class summary changes student/session membership counters; later round IDs increase the observation summary only. Completed and cancelled metadata are immutable. Cancellation retains diagnostic observations but excludes its round from outcomes. Empty explicit completion counts as a legitimate round; zero completed rounds cannot close a version 2 class.

Transactions follow Firebase's [atomicity and retry model](https://firebase.google.com/docs/firestore/manage-data/transactions); cross-document rules use [getAfter validation](https://firebase.google.com/docs/firestore/security/rules-conditions). The installed Android plugin required returning callback errors as values and throwing after native completion: directly throwing from a callback reproduced `Future already completed`. All normal validation/reads precede queued writes. Concurrency also reproduced a rules rejection of a losing create; reconciliation requires server-confirmed owner and exact already-persisted identity, without loosening immutable rules.

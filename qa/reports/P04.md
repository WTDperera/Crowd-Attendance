## Reproduced defects and repairs

The initial eight P04 scenarios all failed against the P03 baseline. A second lecturer could obtain another lecturer's export metadata (HTTP 200), module listing was global, required student catalog/enrollment/attendance queries were denied, direct lecturer enrollment-count changes were allowed, and no trusted password-enrollment endpoint existed. The student-management API also accepted a lecturer UID: PATCH returned 200, changed that lecturer's Auth email and invented a student profile. Synthetic fixtures were reset afterward.

Enrollment now runs in a trusted API transaction. The caller must be an active student, the module must allow enrollment, and the submitted password must match a server-only hash. Concurrent requests produce one enrollment/count increment; repeats preserve other module counters. Wrong passwords remain rejected after enrollment. No body field can choose a different UID or bypass the password. Direct enrollment writes and module enrollment-count edits are denied.

Students discover an explicit safe `module_catalog` projection. Password hashes live in `module_secrets`, unreadable by every client. Raw modules are owner-readable only. Trusted portal module CRUD writes metadata, secrets and catalog together, refuses owner reassignment and prevents deletion of referenced modules. The mobile lecturer mirrors session totals/dates into the catalog in the existing transaction; changes to round/finalization semantics remain later work.

API module/session report and export handlers require ownership before reading metadata or student records. Module lists are owner-filtered. Firestore permits actual student own-record queries and owner session/nested attendance/absence operations, rejects other owners and identity rebinding, and restricts lecturer counter changes to an enrolled module owned by that lecturer. Global lecturer student CRUD remains the approved P01 scope; it does not grant cross-owner reports.

Student management refuses lecturer identities and unknown/protected fields. Creation rolls Auth back if profile persistence fails. Deletion records a durable intent, blocks access, disables Auth, archives historical identity, removes active enrollment/profile, decrements counts once, then removes Auth. Retrying a partial deletion resumes without another decrement. Historical attendance/absence documents remain, and report/export readers include the archived identity. API token validation checks disabled/revoked/deleted accounts.

## Limits and deferred work

- This is local synthetic QA evidence. No live role audit, catalog/secret migration, deployment or production request was performed. Existing live modules would need a reviewed Admin backfill of safe catalog/secret documents before adopting these client/rule changes. Legacy root hashes can be read only by their owner; trusted metadata updates move those hashes into secrets. No broad migration script was added.
- Non-QA Android enrollment now requires an explicit HTTPS `API_BASE_URL` build define. QA uses fixed port 5000. Production endpoint provisioning is outside this phase.
- Deletion is a recoverable workflow, not an Auth/Firestore atomic transaction. Create rollback failure, update rollback failure and all concurrent CRUD races were not fault-injected. Deletion supports up to 100 enrolled modules per student, rejects inconsistent enrollment counts, and may remain disabled/pending until an operator retries or repairs the data. Those limits do not affect the demo fixtures.
- Archived identity keeps records exportable; historical roster eligibility and report mathematics remain P07. Exact registration format/uniqueness/byte budget and device reset policy remain unresolved later validation requirements; no policy was invented here.
- P05/P06 still must fix durable rounds, count/finalization correctness, retry/recovery and ordinary writes after close. The owner counter guard establishes ownership and field boundaries, not correct attendance totals. Several-round behavior was not redesigned or claimed passed.
- Full-app Flutter analysis and baseline portal lint were not rerun. P02's recorded nonzero baseline remains; targeted checks above cover changed sources. Gradle/AGP/Kotlin future-support, Java native-access, AOSP Play Services and portal bundle-size warnings persist; exercised Android checks/builds passed.
- Windows desktop/host tests remain explicitly deferred by the user. Normal UI/browser journeys, physical BLE, human usability, full regression, load/CI and deployment were not run. These tests do not establish E01–E23 or complete security closure.
- Raw synthetic CLI/Firebase logs, caches and generated builds stay ignored and are not publication artifacts. All QA sessions were stopped: final adb device list empty and ports 8080/9099/4400/5000/5580 had no listeners.

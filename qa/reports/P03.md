## Reproduced defects and resulting behavior

Before changing the application rules, a student-identity rules client created `lecturers/qa-student-a`. The actual local Express password-login endpoint then returned HTTP 200 and a portal custom token for that student's credentials. The regression printed `REPRODUCED: student-created lecturer profile yields portal custom token (HTTP 200).` The profile was removed in finally; all later cases begin with a fresh synthetic seed.

The first baseline run had 5 pass/9 fail, including downstream failures after a successful forbidden deletion. Added per-test reset to avoid that contamination; the corrected isolated baseline had **6 pass/8 fail**. It exposed profile provisioning/deletion, identity/counter tampering, replacement binding and student-owned lecturer-resource creation. The post-repair run initially had 13 pass/1 fail because writing an unchanged empty device_id was a harmless no-op in the legacy-empty fixture. The assertion now includes a lock timestamp so it attempts an actual invalid binding; no test was deleted. Added trusted provisioning and further deletion/API/concurrency assertions. The final suite passes **15/15**, zero skips.

The design retains `lecturers/{uid}` as the authoritative role registry, but makes its creation/deletion Admin-only. This closes the reproduced client self-promotion path without adding a second role system or changing the approved lecturer/dashboard credentials. Profile existence is now trusted only under these rules and audited Admin provisioning; this does not retroactively establish the origin of existing live documents.

## Limits and remaining work

- **Local verification only.** Existing live lecturer profiles may have been created under the old permissive rules. Their origin/identity must be audited by a trusted operator before future deployment; these changes alone cannot distinguish a historical forged document. No live data or deployed rules were inspected, changed or migrated.
- **P04–P06 remain unstarted.** Trusted enrollment, legitimate module discovery/nested attendance/absence permissions, API resource ownership/export checks and counter/round integrity are not closed. Current student enrollment writes remain denied and require the planned trusted P04 flow. Do not claim all E05/E06, E04 or U2 pass from this phase.
- **Profile scope:** E02's reproduced promotion is repaired; E03 token-role denials and profile portions of E05 pass under the fixture. Student registration updates through authorized lecturer CRUD remain unchanged; D09's detailed validation/reset policy is not silently resolved.
- **Binding limits:** build-ID/device strings are not unique-phone identity or attestation; rules protect immutable stored binding but cannot prove the caller physically uses the bound phone. Authorized reset workflow remains deferred. No physical BLE or spoof-proof claim.
- **Unrun:** normal UI/browser journeys, student login widget operation, production provisioning, provisioning CLI rollback failure injection, account lifecycle recovery, Windows desktop, iOS, full-app lint/analysis, CI/load/deployment and real-device tests. Student SDK probe validates login write shape rather than UI interaction. New probe analysis is clean; existing full-app/web baseline findings in P02 remain unresolved.
- No new dependencies, secrets or real identities were introduced. Seeds are synthetic and Admin setup does not establish client permissions; rejection/positive rules tests and Android SDK operations do.

Implementation follows Firebase's [field allowlists/diff rules](https://firebase.google.com/docs/firestore/security/rules-fields) and [role-based access and Admin trust boundary](https://firebase.google.com/docs/firestore/solutions/role-based-access). These documents support the mechanism; actual pass/fail evidence is from local execution above.
